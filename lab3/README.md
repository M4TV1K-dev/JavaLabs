# Лабораторная работа №3: Информационная система приюта животных

## 1. Назначение приложения
Приложение представляет собой REST-сервис для автоматизации процессов приюта животных и передачи питомцев в семью (усыновления). Сервис обеспечивает учет вольеров, учет поступивших и размещенных животных, ведение пользователей (заявителей и волонтеров), подачу и обработку заявок на усыновление, а также документальное оформление актов передачи животных.

---

## 2. Предметная модель данных (Сущности и связи)

Данные хранятся в реляционной базе данных. Отношения между таблицами строго регламентированы внешними ключами и ограничениями целостности:

* **Вольер (`enclosures`)**
  * `id` (BIGSERIAL, PK) — уникальный номер.
  * `name` (VARCHAR) — наименование/номер вольера.
  * `allowed_animal_types` (VARCHAR) — допустимые виды животных для совместного размещения.
  * `capacity` (INT, `CHECK (capacity > 0)`) — максимальная вместимость.

* **Животное (`animals`)**
  * `id` (BIGSERIAL, PK).
  * `name` (VARCHAR) — кличка.
  * `species` (VARCHAR) — биологический вид (Собака, Кошка и т.д.).
  * `age` (INT, `CHECK (age >= 0)`) — возраст.
  * `placement_status` (VARCHAR) — текущий статус (`IN_SHELTER`, `QUARANTINE`, `ADOPTION_IN_PROGRESS`, `ADOPTED`).
  * `enclosure_id` (FK `enclosures(id) ON DELETE SET NULL`) — вольер, в котором содержится животное. При удалении вольера животное не удаляется, а его привязка к вольеру сбрасывается.

* **Пользователь (`users`)**
  * `id` (BIGSERIAL, PK).
  * `name` (VARCHAR) — ФИО заявителя/волонтера.
  * `email` (VARCHAR, UNIQUE) — уникальный адрес электронной почты.
  * `phone` (VARCHAR) — контактный телефон.
  * `role` (VARCHAR) — роль (`ADOPTER`, `VOLUNTEER`, `ADMIN`).
  * `created_at` (TIMESTAMP) — дата регистрации.

* **Заявка на усыновление (`adoption_applications`)**
  * `id` (BIGSERIAL, PK).
  * `animal_id` (FK `animals(id) ON DELETE CASCADE`) — усыновляемое животное.
  * `applicant_id` (FK `users(id) ON DELETE CASCADE`) — заявитель.
  * `status` (VARCHAR) — статус заявки (`SUBMITTED`, `APPROVED`, `REJECTED`, `COMPLETED`, `REJECTED_QUARANTINE`).
  * `created_at` (TIMESTAMP) — дата подачи заявки (задается строго сервером).

* **Акт передачи (`animal_handover_records`)**
  * `id` (BIGSERIAL, PK).
  * `application_id` (FK `adoption_applications(id) ON DELETE CASCADE`) — связанная одобренная заявка.
  * `preparation_date` (TIMESTAMP) — дата составления акта (задается сервером).
  * `confirmation_date` (TIMESTAMP) — фактическая дата передачи животного (задается сервером при подтверждении).
  * `status` (VARCHAR) — статус акта (`PREPARED`, `CONFIRMED`, `CANCELLED`).

## 3. Реализованные бизнес-операции

Помимо стандартных CRUD-операций, в сервисе реализовано 5 сквозных бизнес-операций с проверкой инвариантов и согласованным изменением состояния связанных сущностей:

### 1. Заселение животного в вольер
* **Эндпоинт:** `POST /api/operations/assign-enclosure?animalId={id}&enclosureId={id}`
* **Задействованные сущности:** `Animal` + `Enclosure`.
* **Правила и инварианты:**
  * Запрещено заселять животных со статусом `ADOPTED` (уже усыновленные).
  * Запрещено переводить в общий вольер животных из изолятора со статусом `QUARANTINE`.
  * Вид животного (`species`) обязан входить в перечень `allowedAnimalTypes` вольера (нельзя подселить кошку к собакам).
  * Текущее количество жильцов вольера строго меньше его `capacity`.
* **Результат:** Животному присваивается `enclosureId`, статус переводится в `IN_SHELTER`.

### 2. Подача заявки на усыновление
* **Эндпоинт:** `POST /api/operations/submit-application?animalId={id}&applicantId={id}`
* **Задействованные сущности:** `AdoptionApplication` + `Animal` + `User`.
* **Правила и инварианты:**
  * Заявитель должен существовать в системе.
  * Животное должно быть доступно для передачи (`placementStatus == "IN_SHELTER"`). Нельзя подать заявку на больное животное на карантине или уже переданное в другую семью.
  * Запрещены дублирующие заявки: у одного пользователя не может быть более одной активной заявки на одно и то же животное.
* **Результат:** Создается заявка в статусе `SUBMITTED`, текущее животное резервируется (`ADOPTION_IN_PROGRESS`).

### 3. Одобрение заявки и подготовка акта передачи
* **Эндпоинт:** `POST /api/operations/approve-application/{applicationId}`
* **Задействованные сущности:** `AdoptionApplication` + `AnimalHandoverRecord`.
* **Правила и инварианты:**
  * Заявка обязана быть в исходном статусе `SUBMITTED`. Нельзя повторно одобрить уже одобренную, отклонённую или завершённую заявку.
* **Результат:** Заявка переходит в статус `APPROVED`. Автоматически создается связанный документ — акт передачи `AnimalHandoverRecord` со статусом `PREPARED` и серверным временем подготовки.

### 4. Подтверждение передачи животного (Закрытие акта)
* **Эндпоинт:** `POST /api/operations/confirm-handover/{recordId}`
* **Задействованные сущности:** `AnimalHandoverRecord` + `AdoptionApplication` + `Animal` + `Enclosure`.
* **Правила и инварианты:**
  * Акт передачи должен находиться строго в статусе `PREPARED`.
  * Связанная заявка должна быть в статусе `APPROVED`.
* **Результат:** 
  1. Акт переходит в `CONFIRMED`, сервер фиксирует дату подтверждения `confirmationDate`.
  2. Заявка закрывается со статусом `COMPLETED`.
  3. Животное получает окончательный статус `ADOPTED`.
  4. Животное выписывается из вольера (`enclosureId = null`), освобождая место для новых питомцев.

### 5. Экстренный перевод животного на карантин
* **Эндпоинт:** `POST /api/operations/quarantine-animal/{animalId}`
* **Задействованные сущности:** `Animal` + `AdoptionApplication`.
* **Правила и инварианты:**
  * Запрещено отправлять на карантин уже усыновленное животное (`ADOPTED`).
  * Нельзя повторно перевести на карантин животное, уже находящееся на карантине.
* **Результат:**
  1. Животное изолируется (`placementStatus = "QUARANTINE"`), выселяется из вольера (`enclosureId = null`).
  2. Все активные нерассмотренные заявки на это животное (`SUBMITTED`) автоматически аннулируются/отклоняются (`REJECTED_QUARANTINE`), предотвращая передачу заболевшего питомца.

## 4. Конфигурация БД и безопасность (Переменные окружения)

Чувствительные данные для подключения к базе данных вынесены в переменные окружения:

| Переменная | Описание | Значение по умолчанию |
|---|---|---|
| `DB_URL` | JDBC URL подключения к БД | `jdbc:h2:mem:shelter_db;MODE=PostgreSQL...` (H2 в режиме совместимости с PostgreSQL) |
| `DB_USER` | Имя пользователя БД | `shelter_service` |
| `DB_PASSWORD` | Пароль пользователя БД | `shelter_pass` |

* **Для работы с PostgreSQL:**
  Достаточно задать переменные окружения:
  ```powershell
  $env:DB_URL="jdbc:postgresql://localhost:5432/shelter_db"
  $env:DB_USER="shelter_service"
  $env:DB_PASSWORD="shelter_pass"
  ```
  И выполнить DDL скрипт создания служебного пользователя с ограниченными правами из `src/main/resources/init_roles.sql`.
* **По умолчанию (без настройки PostgreSQL):**
  Приложение автоматически поднимает встроенную базу данных H2 в режиме эмуляции PostgreSQL и инициализирует схему из `schema.sql` и тестовые данные из `data.sql`.
